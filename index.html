皮卡丘靶场搭建记录（一）：XAMPP 无管理员权限部署与暴力破解初体验

皮卡丘靶场搭建记录（一）

作业要求：小组讨论完成皮卡丘靶场搭建，个人开始尝试通关，过程记入 blog；高阶要求：通过分析源码，总结漏洞成因，如何修复。

一、皮卡丘是什么

皮卡丘（Pikachu）是一个专为 Web 安全初学者设计的中文漏洞练习平台，源码托管在 GitHub（zhuifengshaonianhanlu/pikachu）。它把常见的 Web 漏洞做成了一个个独立的关卡：

暴力破解、XSS、CSRF、SQL 注入、RCE、文件包含、文件上传、SSRF、XXE、反序列化、目录遍历、越权、任意文件下载、URL 重定向、敏感信息泄露……共 15 大类几十个小关。

二、环境方案

目标是不装虚拟机、不动系统设置，在 Windows 上直接跑起来。最终选型：

组件 选择 说明
Web 环境 XAMPP 8.2.12 便携版（7z 压缩包） 免安装、不需要管理员权限
Web 服务 Apache（XAMPP 自带） 监听 80 端口
数据库 MariaDB 10.4.32（XAMPP 自带） root 空密码，正好匹配 pikachu 默认配置
靶场 pikachu 最新 master 源码 3.6MB，直接解压到 htdocs

为什么用便携版：XAMPP 安装版要 UAC 提权装服务，便携版解压即用，Apache/MySQL 都以普通进程运行，不需要管理员权限，也不污染系统。

五、高阶：源码分析与修复

打开 vul/burteforce/bf_form.php，核心逻辑就 20 行：

漏洞成因，三层都有问题：

  1. 没有验证码：请求可以无限次机械重放，机器可以以任意速率枚举；
  2. 没有失败限制和频控：不锁定账号、不限速、不记录告警，字典再大也只是时间问题；
  3. 响应可区分：成功/失败的提示差异明显，给自动化枚举提供了判断依据。

顺带注意一个”反例”：这段代码用了预编译（prepare + bind_param），SQL 注入在这关是不存在的——pikachu 有意把两个漏洞分开出题。所以漏洞判断要基于代码逐处分析，不能”这个页面有漏洞，那它哪儿都有漏洞”。

修复方案（按性价比排序）：

措施 说明
验证码/行为验证 打断自动化重放，是最直接的一层（图形验证码、滑块、无感行为验证）
失败锁定 + 限速 同一账号连续失败 N 次锁定一段时间；同一 IP 限制单位时间请求数
统一错误提示 成功/失败之外不透露更多信息（此页已算合格，但不要提示”用户不存在/密码错误”的细节差异）
多因素认证（MFA） 密码即使被爆出来，也没有第二因子登录不了
监控告警 登录接口的失败率突增本身就是入侵前兆，应接入告警

六、后续通关计划

剩余模块将按这个顺序逐关记录（每关都按”现象 → 原理 → 源码分析 → 修复”四段式整理）：

  • 暴力破解（基于表单）
  • SQL 注入（数字型 / 字符型 / 搜索型 / xx型 / insert/update / delete / http header）
  • XSS（反射 / 存储 / DOM）
  • RCE（exec ping / eval）
  • 文件包含 / 文件上传
  • CSRF / SSRF / XXE
  • 反序列化 / 越权 / 目录遍历 / 敏感信息泄露 / 任意文件下载 / URL 重定向

QQ流量分析实验：PC-PC端与PC-手机端（Wireshark）

课程作业：针对自己使用的QQ，回答以下问题——使用 UDP 还是 TCP？传输是加密还是明文？能否恢复可能为明文传输的文件？实验全程注意保护个人隐私信息，本文中涉及 IP、账号等敏感内容均已做打码或脱敏处理。

一、实验环境

  • 操作系统：Windows 10/11
  • 抓包工具：Wireshark
  • 联网方式：手机开启热点，PC 通过 WLAN 连接（便于同时观察 PC 与手机端的流量）
  • 本机 IP：192.168.43.50（手机网关为 192.168.43.1）

先用 ipconfig 确认本机 IP 地址和网关，确定要抓取的网卡为 WLAN：

二、抓包准备

打开 Wireshark，选择 WLAN 网卡开始捕获。由于背景流量非常嘈杂（IPv6 组播、Keep-Alive、重传等大量无关报文），第一件事是加显示过滤器，只看本机的流量：

三、问题1：UDP or TCP？

观察捕获到的 QQ 相关流量，可以得出结论：

QQ 的登录、消息收发等核心业务主要走 TCP（443 端口），同时也会使用少量 UDP。

从抓包结果可以看到大量与远端服务器（如 36.150.72.74、120.133.65.237 等）之间 443 端口的 TCP 连接，包含完整的三次握手、ACK、Keep-Alive、FIN 握手拆除等 TCP 特征报文；同时也出现了 DNS 查询（oth.eve.mdt.qq.com 等）这类辅助性的 UDP 流量。

进一步用 tcp.stream / udp 过滤器细分后确认：

  • 文件传输、图片收发、消息同步：TCP（部分走 HTTP 明文，见下文）
  • 语音/视频通话：以 UDP 为主（低延迟考虑）
  • DNS 解析：UDP 53

四、问题2：加密 or 明文？

在过滤器中观察协议列，QQ 的绝大部分流量都是 SSL/TLS 加密的：

  • 443 端口的 TCP 流被 Wireshark 识别为 SSL / TLSv1.2 应用数据，Follow TCP Stream 后看到的是密文，无法直接阅读。

但是，在 PC-手机端（即本机与手机热点网关之间）发现了例外：QQ 的在线图片/文件传输走了 HTTP 明文！

过滤后可以清楚看到一条 HTTP 报文：

几个有意思的点：

  1. 服务器是手机本身（192.168.43.1:8082，HTTP 头里 Server: QQ/1.0.0 (Tencent)），说明这是手机 QQ 作为”中转”向 PC QQ 在线推送文件/图片，符合题目里”在线传输方式“的提示。
  2. URL 路径和 token 看起来是 Base64 编码的，但文件内容本身是明文直接随 HTTP 响应体传输的——这就是可以恢复的文件。

结论：QQ 常规消息/信令走 443 加密；而 PC-手机端在同一局域网下的图片”在线传输”走的是 HTTP 明文，响应体就是原始文件字节。

五、问题3：恢复明文传输的文件

1. 导出 HTTP 对象

对这条流 追踪 HTTP 流 (tcp.stream eq 51)，切换到”原始数据”视图，可以看到响应体开头直接出现了 JPEG 的二进制特征：

FF D8 FF 正是 JPEG 文件的文件头（魔数），Content-Length: 4429569 也与图片大小吻合。

也可以直接用 Wireshark 菜单：文件 → 导出对象 → HTTP，把这个对象保存下来，命名为 reversed_qq.jpg。

2. 修复文件头

直接双击打开 reversed_qq.jpg 会提示”无法打开此图片”。用 HxD 打开十六进制查看，发现问题：

导出的文件把整段 HTTP 报文（GET 请求 + 响应头）都带上了，也就是说真正的 JPEG 数据前面粘了一段 HTTP 文本头，导致图片查看器不认识。

修复方法很简单：找到 JPEG 的真实魔数 FF D8 FF E0（即十六进制 ffd8ffe5...）所在的偏移，把该偏移之前的所有 HTTP 头字节全部删除，让文件以 FF D8 FF 开头，另存为 fix_qq.jpg。

3. 验证

重新打开 fix_qq.jpg——图片成功显示！恢复出来的正是当时通过手机 QQ 在线发送到 PC 的一张游戏战斗截图。

这说明：不同文件类型有不同的”文件头（魔数）”可以作为文件开始的特征码——

文件类型 文件头（十六进制）
JPEG FF D8 FF
PNG 89 50 4E 47 0D 0A 1A 0A
GIF 47 49 46 38
PDF 25 50 44 46
ZIP 50 4B 03 04

只要在明文流量中定位到这些魔数，从该偏移截取到对应文件尾（如 JPEG 的 FF D9），就能恢复出完整文件。

六、结论汇总

问题 结论
UDP or TCP 消息/文件传输以 TCP 为主（443端口），DNS、语音视频等辅助流量使用 UDP
加密 or 明文 常规业务走 TLS 加密；但 PC-手机端局域网内图片在线传输走了 HTTP 明文
文件恢复 可以。通过追踪 HTTP 流/导出对象获取响应体，利用文件魔数（FF D8 FF）定位真实数据起点，删除前置的 HTTP 头即可还原图片

七、隐私保护说明

  • 文中所有 IP 地址为局域网私有地址，已无隐私风险；
  • 涉及 QQ 号、URL token、好友昵称、设备信息的截图均已打码；
  • 抓包文件（pcapng）不对外分享，如需分享应先用 Wireshark 的编辑/脱敏功能去除敏感帧。

对等保2.0的理解

欢迎来到我的博客！

对等保2.0的理解

作为信息安全专业的大学生，我之前完全没接触过网络安全合规相关知识，最开始听到“等保2.0”这个词，会觉得特别专业、很难懂。但慢慢了解后发现，它其实就是国家给所有网络系统制定的一套统一、通用的网络安全规矩，是各行各业做网络安全的基础标准，一点都不抽象。

简单来说，等保的全称是网络安全等级保护，我们可以把它类比成校园安全管理制度。学校会根据教学楼、食堂、档案室、机房的重要程度，制定不一样的安保规则，重要的地方管控更严格。等保2.0也是同一个逻辑，国家根据企业、单位的网络系统的重要性，以及系统出问题后造成的危害大小，划分不同安全等级，每个等级都有对应的防护要求，要求所有运营单位必须照着标准做好网络安全防护。

在等保2.0之前还有等保1.0，是很早的旧标准。那时候互联网形式简单，大多只是普通网站、办公系统，防护要求也比较基础，基本是出了问题再补救，属于被动防护。但随着云计算、大数据、物联网、手机移动端系统越来越普及，网络攻击、数据泄露的风险大幅增加，旧的标准已经跟不上时代，所以国家推出了全面升级的等保2.0新标准，在2019年正式全面落地，也是目前国内唯一通用的网络安全合规标准。

和旧版本相比，等保2.0最大的变化就是覆盖更广、要求更严、防护更主动。以前1.0只针对传统的电脑系统、普通网站，而2.0把云计算、大数据、物联网、工控系统这些新型网络场景全部纳入保护范围，几乎涵盖了我们现在用到的所有网络服务。同时它不再局限于出事之后整改，而是要求做到事前预防、事中监测、事后追溯的全流程防护，从被动堵漏变成主动防御。

另外我了解到，等保2.0把所有网络系统分成了五个等级，等级越低要求越宽松，等级越高安全标准越严苛。普通小型网站、简单办公系统一般是一级、二级，银行、政务平台、医疗系统这类关乎民生和公共安全的核心系统，大多是三级甚至四级，需要定期备案、测评、整改，严格落实安全要求。日常我们听到企业做“等保测评”，就是按照2.0的标准检查系统是否符合安全规范。

对于我们大学生而言，不用深究复杂的技术测评细节，核心记住两个关键点就够了。第一，等保2.0是国家法定的网络安全基础制度，所有正规的网络项目、企业系统都必须遵守，不是可选规则，而是硬性合规要求。第二，它的核心目的很简单，就是统一网络安全标准，避免各行各业网络系统防护参差不齐，防止出现大规模的数据泄露、网络瘫痪、网络攻击问题，保障网络环境安全稳定。

总的来说，等保2.0就是新时代的网络安全“通用准则”，补齐了旧标准的漏洞，适配了当下所有新型网络技术，是网络安全行业的基础和底线。学好、了解等保2.0，也是我们网络安全专业学生入门行业、了解合规体系的必备基础。
