QQ流量分析实验：PC-PC端与PC-手机端（Wireshark）

课程作业：针对自己使用的QQ，回答以下问题——使用 UDP 还是 TCP？传输是加密还是明文？能否恢复可能为明文传输的文件？实验全程注意保护个人隐私信息，本文中涉及 IP、账号等敏感内容均已做打码或脱敏处理。

一、实验环境

  • 操作系统：Windows 10/11
  • 抓包工具：Wireshark
  • 联网方式：手机开启热点，PC 通过 WLAN 连接（便于同时观察 PC 与手机端的流量）
  • 本机 IP：192.168.43.50（手机网关为 192.168.43.1）

先用 ipconfig 确认本机 IP 地址和网关，确定要抓取的网卡为 WLAN：

二、抓包准备

打开 Wireshark，选择 WLAN 网卡开始捕获。由于背景流量非常嘈杂（IPv6 组播、Keep-Alive、重传等大量无关报文），第一件事是加显示过滤器，只看本机的流量：

三、问题1：UDP or TCP？

观察捕获到的 QQ 相关流量，可以得出结论：

QQ 的登录、消息收发等核心业务主要走 TCP（443 端口），同时也会使用少量 UDP。

从抓包结果可以看到大量与远端服务器（如 36.150.72.74、120.133.65.237 等）之间 443 端口的 TCP 连接，包含完整的三次握手、ACK、Keep-Alive、FIN 握手拆除等 TCP 特征报文；同时也出现了 DNS 查询（oth.eve.mdt.qq.com 等）这类辅助性的 UDP 流量。

进一步用 tcp.stream / udp 过滤器细分后确认：

  • 文件传输、图片收发、消息同步：TCP（部分走 HTTP 明文，见下文）
  • 语音/视频通话：以 UDP 为主（低延迟考虑）
  • DNS 解析：UDP 53

四、问题2：加密 or 明文？

在过滤器中观察协议列，QQ 的绝大部分流量都是 SSL/TLS 加密的：

  • 443 端口的 TCP 流被 Wireshark 识别为 SSL / TLSv1.2 应用数据，Follow TCP Stream 后看到的是密文，无法直接阅读。

但是，在 PC-手机端（即本机与手机热点网关之间）发现了例外：QQ 的在线图片/文件传输走了 HTTP 明文！

过滤后可以清楚看到一条 HTTP 报文：

几个有意思的点：

  1. 服务器是手机本身（192.168.43.1:8082，HTTP 头里 Server: QQ/1.0.0 (Tencent)），说明这是手机 QQ 作为”中转”向 PC QQ 在线推送文件/图片，符合题目里”在线传输方式“的提示。
  2. URL 路径和 token 看起来是 Base64 编码的，但文件内容本身是明文直接随 HTTP 响应体传输的——这就是可以恢复的文件。

结论：QQ 常规消息/信令走 443 加密；而 PC-手机端在同一局域网下的图片”在线传输”走的是 HTTP 明文，响应体就是原始文件字节。

五、问题3：恢复明文传输的文件

1. 导出 HTTP 对象

对这条流 追踪 HTTP 流 (tcp.stream eq 51)，切换到”原始数据”视图，可以看到响应体开头直接出现了 JPEG 的二进制特征：

FF D8 FF 正是 JPEG 文件的文件头（魔数），Content-Length: 4429569 也与图片大小吻合。

也可以直接用 Wireshark 菜单：文件 → 导出对象 → HTTP，把这个对象保存下来，命名为 reversed_qq.jpg。

2. 修复文件头

直接双击打开 reversed_qq.jpg 会提示”无法打开此图片”。用 HxD 打开十六进制查看，发现问题：

导出的文件把整段 HTTP 报文（GET 请求 + 响应头）都带上了，也就是说真正的 JPEG 数据前面粘了一段 HTTP 文本头，导致图片查看器不认识。

修复方法很简单：找到 JPEG 的真实魔数 FF D8 FF E0（即十六进制 ffd8ffe5...）所在的偏移，把该偏移之前的所有 HTTP 头字节全部删除，让文件以 FF D8 FF 开头，另存为 fix_qq.jpg。

3. 验证

重新打开 fix_qq.jpg——图片成功显示！恢复出来的正是当时通过手机 QQ 在线发送到 PC 的一张游戏战斗截图。

这说明：不同文件类型有不同的”文件头（魔数）”可以作为文件开始的特征码——

文件类型 文件头（十六进制）
JPEG FF D8 FF
PNG 89 50 4E 47 0D 0A 1A 0A
GIF 47 49 46 38
PDF 25 50 44 46
ZIP 50 4B 03 04

只要在明文流量中定位到这些魔数，从该偏移截取到对应文件尾（如 JPEG 的 FF D9），就能恢复出完整文件。

六、结论汇总

问题 结论
UDP or TCP 消息/文件传输以 TCP 为主（443端口），DNS、语音视频等辅助流量使用 UDP
加密 or 明文 常规业务走 TLS 加密；但 PC-手机端局域网内图片在线传输走了 HTTP 明文
文件恢复 可以。通过追踪 HTTP 流/导出对象获取响应体，利用文件魔数（FF D8 FF）定位真实数据起点，删除前置的 HTTP 头即可还原图片

七、隐私保护说明

  • 文中所有 IP 地址为局域网私有地址，已无隐私风险；
  • 涉及 QQ 号、URL token、好友昵称、设备信息的截图均已打码；
  • 抓包文件（pcapng）不对外分享，如需分享应先用 Wireshark 的编辑/脱敏功能去除敏感帧。
