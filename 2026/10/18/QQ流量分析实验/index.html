QQ流量分析实验（PC-PC端 / PC-手机端）

课程作业：针对自己实际使用的 QQ，回答三个问题——用的是 UDP 还是 TCP？传输是加密还是明文？能否恢复明文传输的文件？ 本文记录完整的抓包、识别、分析与文件还原过程，涉及 IP、账号、token 等敏感信息均已做脱敏处理。

一、实验环境

项目 内容
操作系统 Windows 10 / 11
抓包工具 Wireshark 4.x
十六进制编辑器 HxD
联网方式 手机开启热点，PC 通过 WLAN 连接
本机 IP 192.168.43.50
网关（手机） 192.168.43.1

之所以用手机热点而不是宿舍路由器，是因为热点模式下 PC 与手机处于同一个二层广播域，PC 端的 WLAN 网卡能以"混杂模式"抓到手机与 PC 之间、甚至手机转发给其他设备的全部报文，正好覆盖题目要求的"PC-PC 端 + PC-手机端"两种场景。

先用 ipconfig 确认本机 IP 和默认网关，确定抓包网卡为 WLAN：

二、抓包与初步过滤

打开 Wireshark，双击 WLAN 网卡开始捕获。此时会有大量无关的背景流量（IPv6 邻居发现、各类 App 的心跳 Keep-Alive、TCP 重传等），直接在一千多条报文里找 QQ 是不现实的，第一步一定是加显示过滤器。

# 只看与本机相关的报文
ip.addr == 192.168.43.50

从报文列表可以观察到几个明显的特征：

  • 本机与远端服务器（36.150.72.74、120.133.65.237、120.233.51.170 等）之间大量 443 端口的连接；
  • 出现 [TCP Keep-Alive]、[TCP Retransmission]、[SYN]/[ACK]/[FIN, ACK] 等典型 TCP 行为；
  • 出现 DNS 查询（如 oth.eve.mdt.qq.com），这是 UDP；
  • 8082 端口上有一条 HTTP 报文 —— 这是整次实验的突破口。

三、问题一：UDP 还是 TCP？

3.1 结论

QQ 的核心业务以 TCP 为主，辅助场景使用 UDP。

3.2 分析依据

业务类型 传输层协议 端口 说明
登录、消息收发、文件/图片传输 TCP 443（TLS） 完整三次握手、ACK 确认、Keep-Alive、FIN 拆链，可靠传输
局域网在线文件传输 TCP 8082（HTTP） 明文 HTTP，见下文
DNS 解析 UDP 53 标准查询/响应
语音 / 视频通话 UDP 动态 允许少量丢包，追求低延迟

判断依据来自报文细节：截图中 192.168.43.50 → 36.150.72.74 的报文带有 [SYN]、[ACK]、Seq/Ack/Win 字段，且存在 [TCP Retransmission] 和 [TCP Keep-Alive]。这些都是 TCP 独有的机制——UDP 既没有握手，也没有序列号、确认号、重传和窗口，因此可以明确判定该业务跑在 TCP 上。

四、问题二：加密还是明文？

4.1 大多数流量是加密的

在协议列中可以看到大量 SSL 记录，追踪任意一条 443 端口的 TCP 流，得到的是 TLS 记录层密文（Application Data），无法直接还原出聊天内容或账号信息。

这说明 QQ 的登录鉴权、消息同步等核心信令都经过 TLS 加密，符合现代 IM 的常规设计：即使流量被截获，攻击者也拿不到明文。

4.2 但是在"PC-手机端"发现了明文 HTTP

把过滤器换成只看 8082 端口后，一条 HTTP 报文非常显眼：

GET /qqline/JXy9tEV+PZD1yfMP66ekn4kq2GGer6dVIvvFR4dMZ77WNy8BWk0Y7A==?token=kkXNQdjNfQ/piPLJ9dH0y7ag4EuPPkGlL4szUH8wgcs= HTTP/1.1
Host: 192.168.43.1:8082
Accept: */*
Connection: Keep-Alive
User-Agent: Mozilla/5.0 (compatible; MSIE 10.0; Windows NT 6.2)
Pragma: no-cache
Cache-Control: no-cache

HTTP/1.1 200 OK
Server: QQ/1.0.0 (Tencent)
Content-Length: 4429569
Connection: keep-alive

这段报文信息量很大，逐一拆解：

  1. Host: 192.168.43.1:8082 —— 服务端不是腾讯的公网服务器，而是手机本身（热点网关地址）。说明这是手机 QQ 把自己的某个资源，通过局域网直接"在线分发"给 PC 端 QQ。
  2. Server: QQ/1.0.0 (Tencent) —— 服务端标识直接暴露了应用层身份，确认是 QQ 的组件。
  3. Content-Length: 4429569 —— 响应体约 4.4 MB，远大于普通文本消息，说明传输的是一个文件。
  4. User-Agent: ... MSIE 10.0 ... —— 使用老式 IE 的 UA，是 PC 端内置浏览器内核（CEF/IE 兼容模式）发起的请求，常见于 QQ 内置的"查看图片/文件"预览页。
  5. URL 路径与 token 是一长串 Base64，属于鉴权参数，并不是对内容的加密——响应体本身是裸的原始文件字节。

追踪这条 TCP 流（tcp.stream eq 51），切换到"原始数据"视图，响应头之后紧接着出现：

ffd8ffe5001a495455543538 264...

FF D8 FF 正是 JPEG 的文件头（魔数）。也就是说，图片内容是以明文 HTTP 断点传输的，没有任何加密。

4.3 为什么会出现明文？

本质上这是局域网内的性能优化：当 PC 和手机在同一热点下，QQ 发现"对方就在旁边"，就会放弃"上传到腾讯服务器 → 对方再下载"的公网中转路径，改为局域网直连（类似 P2P 的在线传输）。由于链路本身不可被外部网络监听，实现方在这种场景下简化了协议——直接用一个内嵌的 HTTP 小服务（8082 端口）把文件吐给对端，于是就留下了明文流量。

这也正好对应题目里的提示："在线传输方式"。

⚠️ 安全提示：这意味着在公共 WiFi、宿舍共享网络、公司内网等同网段可被嗅探的环境中，别人完全可能用同样的方法抓走你在线发送的图片、文件。QQ 的加密策略在这里是"按场景降级"的。

五、问题三：恢复明文传输的文件

既然文件是明文，就能完整还原。整个过程分为三步：定位 → 导出 → 修复。

5.1 定位文件边界

可以从两个线索确定文件起止：

  • 起点：JPEG 魔数 FF D8 FF（后面通常跟 E0 表示 JFIF 段）
  • 终点：JPEG 文件尾 FF D9（EOI，End Of Image）
  • 长度：HTTP 头里的 Content-Length: 4429569 给出了精确字节数，可直接校验

5.2 导出对象

方法一（推荐）：Wireshark 菜单 文件 → 导出对象 → HTTP，在弹出的对象列表里找到该请求，保存为 reversed_qq.jpg。

方法二：在追踪流窗口点"另存为"，保存整段流内容。

5.3 修复文件头

导出后双击打开，图片查看器提示"无法打开此图片"——文件损坏了。

用 HxD 打开看十六进制，问题一目了然：

文件偏移 0x00000000 开始的内容是 GET /qqline/JXy9...，也就是整段 HTTP 请求行 + 请求头 + 响应头 + 响应体都被一起保存进来了。操作系统和图片查看器都是靠文件头魔数判断类型的，开头是 G(0x47) 而不是 FF，自然识别失败。

修复方法：在 HxD 中搜索 FF D8 FF（快捷键 Ctrl+F，选择"十六进制值"），记下真实 JPEG 数据的起始偏移，然后选中该偏移之前的全部字节并删除（Ctrl+E 选区起点 → Ctrl+Shift+E 选区终点 → Delete），让文件以 FF D8 FF E0 开头，另存为 fix_qq.jpg。

修复后的文件头：

顺便在数据中还能读到一些明文元信息，进一步佐证这是原始图片：

  • HUAWEI Pura 70 Pro + HBN-AL00 —— 拍摄设备型号
  • 2026:09:19 17:44:20 —— EXIF 拍摄时间
  • Exif、MM、ITU-T35 —— 标准 JPEG/EXIF 结构标识

5.4 验证结果

打开 fix_qq.jpg，图片正常显示：

恢复出来的正是当时通过手机 QQ 在线发送的一张游戏战斗结算截图，画面完整、无损坏。实验成功。

5.5 通用方法论：文件魔数表

这次能成功还原，核心就在于利用文件头特征码定位真实数据的起点。常见文件类型的魔数如下，掌握这张表就能应对绝大多数明文流量中的文件还原：

文件类型 魔数（Hex） ASCII 特征 文件尾
JPEG FF D8 FF ÿØÿ FF D9
PNG 89 50 4E 47 0D 0A 1A 0A .PNG.... 49 45 4E 44 AE 42 60 82（IEND）
GIF 47 49 46 38 39 61 GIF89a 3B
BMP 42 4D BM —
PDF 25 50 44 46 2D %PDF- %%EOF
ZIP 50 4B 03 04 PK.. 中央目录结束记录
RAR 52 61 72 21 1A 07 Rar!.. —

自动化思路（Python 版），比手工删头更适合批量处理：

import re

MAGIC = {
    b"\xff\xd8\xff": ".jpg",
    b"\x89PNG\r\n\x1a\n": ".png",
    b"GIF89a": ".gif",
    b"%PDF-": ".pdf",
    b"PK\x03\x04": ".zip",
}

def carve(pcap_payload: bytes, out_prefix="carved"):
    # 从原始字节流中抠出文件（简化版 carver）
    made = []
    for magic, ext in MAGIC.items():
        for m in re.finditer(re.escape(magic), pcap_payload):
            start = m.start()
            end = start + 1
            if ext == ".jpg":
                # 找 EOI: FF D9
                i = pcap_payload.find(b"\xff\xd9", start)
                if i != -1:
                    end = i + 2
            if end > start + 512:                      # 过滤误匹配
                name = f"{out_prefix}{len(made)}{ext}"
                with open(name, "wb") as f:
                    f.write(pcap_payload[start:end])
                made.append((name, start, end))
    return made

六、结论汇总

题目问题 本次实验结论
UDP or TCP 消息、登录、文件传输均以 TCP 为主（443 + 8082）；UDP 用于 DNS 解析与音视频通话
加密 or 明文 公网业务走 TLS 加密；但 PC-手机端同局域网在线传图走了 HTTP 明文（Server: QQ/1.0.0）
能否恢复文件 可以。用 Content-Length 与 JPEG 魔数 FF D8 FF 定位，删除导出文件前置的 HTTP 头，完整还原 4.4 MB 图片

一句话总结：QQ 把加密做在了"公网链路"上，却把明文留在了"局域网直连"里。 攻击面不在算法强度，而在场景降级。

七、防护建议与隐私说明

用户侧防护：

  1. 不要在不可信的公共 WiFi / 共享网段下传输敏感图片、证件照、合同；
  2. 关闭系统与热点的"网络发现/共享"，避免陌生设备处于同一二层网络；
  3. 重要文件拒绝"原图/原始文件"以外的传输方式（很多 IM 的"文件助手"路径会走公网加密通道）；
  4. 涉及身份证、银行卡的图片，优先用压缩或涂改后的版本发送。

实验侧隐私处理：

  • 本文所有 IP 均为局域网私有地址（RFC1918），不构成真实位置泄露；
  • QQ 号、好友昵称、URL token、设备序列号等已在截图中打码；
  • 抓包文件（.pcapng）不对外分享；如需分享，应先用 Wireshark 编辑 → 首选项 → 协议 → HTTP/TLS 关闭私钥解密，或用 editcap / TraceWrangler 删除敏感帧。
